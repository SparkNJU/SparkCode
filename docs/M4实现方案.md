## 4. 文件详解

### Step 1: `src/compact/meter.ts` — Token 计量（新建）

**职责**：估算文本的 token 数量。方案 B（估算器），不依赖 API 返回的 usage。

```typescript
// compact/meter.ts — token 计量（自研轻量估算器）

/**
 * 估算文本的 token 数量
 * - 中文（CJK）：约 1.6 字符/token
 * - 英文/其他：约 4 字符/token
 * - JSON/代码结构符号（{}[]():）按 2 字符/token
 */
export function estimateTokens(text: string): number {
  let cjk = 0
  let other = 0
  for (const ch of text) {
    if (/[一-鿿　-〿＀-￯]/.test(ch)) {
      cjk++
    } else {
      other++
    }
  }
  return Math.ceil(cjk / 1.6 + other / 4)
}

/**
 * 估算 DerivedMessage[] 的总 token 数
 */
export function estimateMessagesTokens(messages: Array<{ role: string; content: unknown }>): number {
  let total = 0
  for (const msg of messages) {
    // role 标签开销
    total += 4
    if (typeof msg.content === 'string') {
      total += estimateTokens(msg.content)
    } else if (Array.isArray(msg.content)) {
      // AssistantMessage 的 content 是 ContentBlock[]
      for (const block of msg.content) {
        if (block.type === 'text') {
          total += estimateTokens(block.text)
        } else if (block.type === 'tool-call') {
          total += estimateTokens(block.arguments) + estimateTokens(block.name) + 10
        } else if (block.type === 'tool-result') {
          total += estimateTokens(block.content) + 10
        }
      }
    }
  }
  return total
}
```

**设计要点**：
1. **纯函数**：无副作用，无外部依赖，易于测试
2. **中英文分离**：CJK 字符 ~1.6 字符/token，英文 ~4 字符/token（参考 tiktoken 统计）
3. **ContentBlock 感知**：能正确处理 assistant 消息中的 tool-call / tool-result 块
4. **精度目标**：±20% 误差可接受（用于阈值判断，不需要精确计数）

### Step 2: `src/compact/basic.ts` — 结果裁剪 + 摘要压缩（新建）

**职责**：实现两级压缩策略。

#### 4.1 工具结果裁剪（第一级）

```typescript
// compact/basic.ts — 工具结果裁剪

import { estimateTokens } from './meter.js'

/** 裁剪阈值：单个工具结果超过此字符数时触发裁剪 */
const TRIM_THRESHOLD_CHARS = 10_000

/** 裁剪后保留的字符数 */
const TRIM_MAX_CHARS = 4_000

/**
 * 裁剪超长工具结果
 * 策略：头部 80% + 尾部 20% + 落盘提示
 *
 * 与 M3 的 count-based 截断不同：
 * - M3 截断发生在工具内部（glob 1000 条、grep 500 条）
 * - M4 裁剪发生在工具结果进入历史前（兜底保护）
 */
export function trimToolResult(content: string): string {
  if (content.length <= TRIM_THRESHOLD_CHARS) {
    return content
  }

  const headLen = Math.floor(TRIM_MAX_CHARS * 0.8)
  const tailLen = TRIM_MAX_CHARS - headLen

  const head = content.slice(0, headLen)
  const tail = content.slice(-tailLen)

  const dropped = content.length - headLen - tailLen
  const notice = `\n\n... [已裁剪 ${dropped} 字符，原始 ${content.length} 字符] ...\n\n`

  return head + notice + tail
}
```

**设计要点**：
1. **头 80% + 尾 20%**：头部包含文件开头（import、类定义等关键信息），尾部包含文件结尾（export、结论）
2. **落盘提示**：裁剪处插入明确标记，让模型知道内容被截断了
3. **与 M3 截断的关系**：M3 的截断是工具内部的 count-based 截断（glob 1000 条、grep 500 条、read 50K 字符），M4 的裁剪是进入历史前的兜底保护。两者不冲突

#### 4.2 摘要压缩（第二级）

```typescript
// compact/basic.ts — 摘要压缩

import type { DerivedMessage } from '../core/session.js'
import { estimateMessagesTokens } from './meter.js'

/** 摘要压缩配置 */
export interface CompactionConfig {
  /** 触发摘要压缩的 token 阈值 */
  threshold: number
  /** 每次压缩保留最近 N 轮不动 */
  keepRecentTurns: number
  /** 摘要系统提示词 */
  summaryPrompt: string
}

/** 默认配置 */
export const DEFAULT_COMPACTION_CONFIG: CompactionConfig = {
  threshold: 80_000,      // 128K 窗口的 ~62%
  keepRecentTurns: 3,     // 保留最近 3 轮
  summaryPrompt: `你是一个对话摘要助手。请将以下对话历史压缩为简洁的摘要，保留：
1. 用户的核心需求和目标
2. 已完成的关键操作和结果
3. 未完成的任务或待解决的问题
4. 重要的代码文件路径和修改内容

输出纯文本摘要，不要使用 Markdown 格式。`,
}

/**
 * 检查是否需要压缩
 */
export function needsCompaction(messages: DerivedMessage[], config: CompactionConfig): boolean {
  const tokens = estimateMessagesTokens(messages)
  return tokens > config.threshold
}

/**
 * 找到压缩切割点
 * 返回值：要压缩的消息范围 [0, cutIndex)
 * 保留最近 keepRecentTurns 个用户消息之后的所有内容
 */
export function findCompactionCutPoint(messages: DerivedMessage[], keepRecentTurns: number): number {
  let userMessageCount = 0
  let cutIndex = 0

  // 从后往前数 user 消息
  for (let i = messages.length - 1; i >= 0; i--) {
    if (messages[i]!.role === 'user') {
      userMessageCount++
      if (userMessageCount >= keepRecentTurns) {
        cutIndex = i
        break
      }
    }
  }

  // 确保至少压缩一些内容
  if (cutIndex === 0 && messages.length > 10) {
    cutIndex = Math.floor(messages.length * 0.6)
  }

  return cutIndex
}

/**
 * 从消息列表中提取要压缩的文本
 */
export function messagesToSummaryText(messages: DerivedMessage[]): string {
  const parts: string[] = []
  for (const msg of messages) {
    switch (msg.role) {
      case 'user':
        parts.push(`[用户] ${msg.content}`)
        break
      case 'assistant': {
        const textBlocks = msg.content
          .filter(b => b.type === 'text')
          .map(b => b.text)
        if (textBlocks.length > 0) {
          parts.push(`[助手] ${textBlocks.join('')}`)
        }
        const toolCalls = msg.content
          .filter(b => b.type === 'tool-call')
          .map(b => `${b.name}(${b.arguments.slice(0, 100)})`)
        if (toolCalls.length > 0) {
          parts.push(`[工具调用] ${toolCalls.join(', ')}`)
        }
        break
      }
      case 'tool':
        parts.push(`[工具结果] ${msg.content.slice(0, 200)}`)
        break
    }
  }
  return parts.join('\n')
}
```

**设计要点**：
1. **阈值 80K token**：128K 窗口的 ~62%，留够空间给新对话
2. **保留最近 3 轮**：确保模型记得最近的操作上下文
3. **纯文本提取**：将消息历史转为纯文本送给 LLM 做摘要
4. **工具结果只取前 200 字符**：避免摘要请求本身也爆上下文

### Step 3: `src/core/session.ts` — 支持 replace surfaceOp（修改）

**当前问题**：`append()` 的 `surfaceOp` 只支持 `'append'`，不支持 `replace`。

**修改内容**：在 `append()` 方法中增加 `replace` 支持。

```typescript
// session.ts — 修改 append 方法

export class Session {
  // ... 现有代码 ...

  append<T extends SessionEvent['type']>(
    type: T,
    data: Extract<SessionEvent, { type: T }>['data'],
    options?: { surfaceOp?: 'append' | { op: 'replace'; start: number; end: number } },
  ): Extract<SessionEvent, { type: T }> {
    const event = {
      seq: this.seq++,
      time: Date.now(),
      type,
      data,
    } as Extract<SessionEvent, { type: T }>

    this.log.push(event as SessionEvent)

    // Surface 事件增量投影
    if (options?.surfaceOp === 'append') {
      this.projectEvent(event as SessionEvent)
    } else if (options?.surfaceOp && typeof options.surfaceOp === 'object' && options.surfaceOp.op === 'replace') {
      // replace 操作：替换 derivedMessages 中的指定范围
      const { start, end } = options.surfaceOp
      this.derivedMessages.splice(start, end - start)
      // splice 后重新投影此事件（作为替换内容）
      this.projectEvent(event as SessionEvent)
    }

    return event
  }

  // ... 其余不变 ...
}
```

**设计要点**：
1. **`replace` surfaceOp**：`{ op: 'replace', start, end }` 表示删除 `derivedMessages[start..end)`，然后把当前事件投影进去
2. **原始日志不变**：compaction 事件本身也写入日志（可审计），但通过 `replace` 修改模型视角
3. **幂等性**：重放时 `replay()` 也需要处理 replace 操作

private async executeToolCalls(
  calls: Array<{ id: string; name: string; arguments: string }>,
): Promise<void> {
  // ... 记录 tool/call 事件（不变） ...

  // 串行执行
  for (const call of calls) {
    // ... 参数解析（不变） ...

    const result = await this.tools.execute(/* ... */)

    // ★ M4 新增：裁剪超长工具结果

      ? trimToolResult(result.content)

      step: this.step,

        role: 'tool',
        callId: call.id,

      },

  }
}

#### 位置 B：摘要压缩（runTurn 主循环中）

在 LLM 请求之前检查上下文大小，超阈值时触发摘要压缩。

```typescript
// loop.ts — runTurn 主循环修改

import { needsCompaction, findCompactionCutPoint, messagesToSummaryText, DEFAULT_COMPACTION_CONFIG } from '../compact/basic.js'
import { estimateMessagesTokens } from '../compact/meter.js'

private async runTurn(): Promise<boolean> {
  // ... 现有代码到 while(true) 循环 ...

  while (true) {
    // ★ M4 新增：上下文压缩检查
    if (this.config.compaction.enabled) {
      await this.maybeCompactContext()
    }

    // ... 组装 prompt、调用 LLM（不变） ...
  }
}

/**
 * 检查上下文大小，必要时执行摘要压缩
 */
private async maybeCompactContext(): Promise<void> {
  const messages = this.session.deriveMessages()
  const config = this.config.compaction

  if (!needsCompaction(messages, { ...DEFAULT_COMPACTION_CONFIG, threshold: config.threshold })) {
    return
  }

  // 找到压缩切割点
  const cutIndex = findCompactionCutPoint(messages, config.keepRecentTurns)
  if (cutIndex === 0) return // 没有可压缩的内容

  // 提取要压缩的消息
  const toCompact = messages.slice(0, cutIndex)
  const summaryText = messagesToSummaryText(toCompact)

  // 用 LLM 生成摘要（独立请求）
  const summaryPrompt = DEFAULT_COMPACTION_CONFIG.summaryPrompt
  const summaryResult = await this.llm.stream(
    {
      model: this.config.model,
      messages: [
        { role: 'system', content: summaryPrompt },
        { role: 'user', content: summaryText },
      ],
    },
    this.abort!.signal,
  )

  // 提取摘要文本
  const summaryBlock = summaryResult.message.content.find(b => b.type === 'text')
  const summary = summaryBlock?.text ?? '（摘要生成失败）'

  // 用 replace 标记替换模型视角
  // 删除 derivedMessages[0..cutIndex)，插入摘要消息
  this.session.append('agent/inbox/spliced', {
    target: 'next-step',
    messages: [{
      id: generateId(),
      role: 'user',
      content: `[对话摘要]\n${summary}`,
      source: 'injected',
    }],
  }, {
    surfaceOp: {
      op: 'replace',
      start: 0,
      end: cutIndex,
    },
  })

  // 广播压缩事件（供 UI 显示）
  this.ctx.emit('compact/done', {
    originalTokens: estimateMessagesTokens(toCompact),
    summaryTokens: estimateTokens(summary),
    cutIndex,
  })
}
```

**设计要点**：
1. **两级压缩独立运作**：工具结果裁剪是无条件的（只要超长就裁），摘要是有条件的（超阈值才触发）
2. **摘要用独立 LLM 请求**：不污染当前对话的 token 预算
3. **replace surfaceOp**：只修改模型视角，原始日志保留
4. **UI 广播**：`compact/done` 事件让 TUI/Web 可以显示"已压缩 N token → M token"

## 6. 关键设计决策（答辩准备）

### Q: 为什么用两级压缩而不是一级？

**A**：两级压缩解决不同粒度的问题：
- **第一级（工具结果裁剪）**：解决"单次工具返回超长"的问题——比如 read 一个 100KB 的文件。裁剪是即时的、无成本的。
- **第二级（摘要压缩）**：解决"累积对话过长"的问题——50 轮对话后上下文超限。需要 LLM 生成摘要，有 API 调用成本。

如果只有第一级，长对话仍然会爆；如果只有第二级，单次超长工具结果会浪费大量 token。两级配合是最优解。

### Q: 摘要压缩的时机是什么？为什么不每轮都压缩？

**A**：摘要压缩在"上下文超过阈值"时触发，不是每轮都做。原因：
1. **成本**：每次摘要需要一次独立 LLM API 调用
2. **延迟**：摘要请求会阻塞当前回合
3. **信息损失**：摘要是有损压缩，过早压缩会丢失有用细节

阈值设为 80K token（128K 窗口的 62%），在还有余量时提前压缩，避免最后几轮因为上下文过长而失败。

### Q: 摘要压缩为什么用独立 LLM 请求而不是在当前请求中做？

**A**：(1) 当前请求的上下文已经接近上限，无法再塞入"请帮我摘要"的指令；(2) 独立请求可以用更简单的 system prompt，不干扰编程助手的角色设定；(3) 独立请求可以使用更便宜的模型（未来扩展）。

### Q: replace surfaceOp 如何保证可审计性？

**A**：原始日志（`session.log`）永远不会被修改。compaction 操作本身也写入日志（`agent/inbox/spliced` 事件），只是通过 `surfaceOp: { op: 'replace' }` 修改了模型可见的消息表面（`derivedMessages`）。这意味着：
- 模型视角：看到的是压缩后的摘要
- 审计视角：可以通过原始日志还原完整对话
- UI 视角：可以显示"已压缩"标记，并提供展开原始对话的能力

### Q: token 估算的精度够用吗？

**A**：用于阈值判断，±20% 误差完全够用。我们设 80K 阈值，即使实际是 64K~96K，也不会有问题——因为 128K 窗口还有足够的 buffer。精确计数需要调用 tiktoken 库，增加外部依赖，不符合"核心逻辑自研"原则。

### Q: 为什么保留最近 3 轮而不是更多/更少？

**A**：3 轮是一个平衡点——足够模型理解"我刚才在做什么"（比如"我正在编辑 src/auth.ts"），又不会保留太多历史浪费 token。对于编程场景，最近 3 轮通常包含：(1) 用户最新指令；(2) 助手的工具调用和结果；(3) 助手的回复。这三轮覆盖了"当前任务上下文"的核心信息。
